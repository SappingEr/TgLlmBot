## Сворачивание длинных ответов

Ответы LLM сворачиваются в блок «Развернуть ответ», если текст всего ответа для истории
превышает 600 символов или 8 строк. Markdown-разметка в длину не входит; строки считаются
по явным переносам, а не по ширине экрана. Короткие ответы отображаются полностью.
Порог длины считается по кодовым точкам Unicode: `😀` — одна, `e` с отдельным комбинируемым
акцентом — две. URL ссылок входят в длину текста для истории, даже если в HTML видна только подпись.

Настройки секции `Telegram` в `appsettings.json` или переменных окружения:

- `Telegram__CollapseLongResponses` — включение сворачивания, по умолчанию `true`.
- `Telegram__ResponseCollapseCharacterThreshold` — порог символов, по умолчанию `600`.
- `Telegram__ResponseCollapseLineThreshold` — порог строк, по умолчанию `8`.

Пороги должны быть положительными. Ответ делится на части с текстом до 4096 символов,
каждая часть сохраняется отдельной записью истории. У длинного ответа все части сворачиваются;
если частей несколько, в заголовке каждого ката отображается номер части.
При выключенном сворачивании части отображаются полностью. Для отправки используется
Telegram Bot API Rich Messages; код, списки, ссылки и таблицы сохраняют форматирование.
При ошибке разметки отправляется упрощённый текст с тем же катом.
Если после отправки части ответа оставшиеся части отправить не удалось, бот сообщает об обрыве
в том же чате и теме. Это уведомление не сохраняется в истории. Сбой сохранения после отправки
последней части не вызывает повторную отправку ответа или уведомление об обрыве.

## Тесты форматтера и отправки ответов

Проект `tests/TgLlmBot.Tests/` использует xUnit.net v3 (`xunit.v3.mtp-v2`) и
Microsoft.Testing.Platform. Запуск из корня репозитория с SDK из `global.json`:

```bash
dotnet test --solution TgLlmBot.slnx -c Release
dotnet build TgLlmBot.slnx -c Release
```

Workflow `.github/workflows/dotnet.yml` запускает восстановление зависимостей, Release-сборку
и тесты для каждого pull request и при push в `main`. SDK выбирается из `global.json`.
Тестовый шаг завершается ошибкой, если не найдено ни одного теста. Workflow также можно запустить вручную.

Тесты вызывают публичные `DefaultLlmResponseFormatter` и `LlmResponsePart` с настоящим
Markdown-парсером. Проверки `DefaultLlmChatHandler` используют подменённый `HttpMessageHandler`
для ответов Telegram, фиксированный ответ LLM и хранилище в памяти.
Запуск бота, настоящие токены, PostgreSQL и доступ к LLM или Telegram не требуются.
Имена тестов следуют формату `НазваниеМетода_ПараметрыИлиУсловия_ОжидаемыйРезультат`.

Файлы в `tests/TgLlmBot.Tests/Commands/ChatWithLlm/Services/` сгруппированы по поведению:

- `DefaultLlmResponseFormatterTests.cs` — примеры Markdown → текст истории и HTML,
  нормализация переносов, повреждённый UTF-16 и буквальный текст.
- `DefaultLlmResponseFormatterCollapseTests.cs` — границы порогов, подсчёт Unicode и строк,
  общий порог для нескольких частей, выключенное сворачивание и номера частей.
- `DefaultLlmResponseFormatterSplittingTests.cs` — лимит 4096 единиц UTF-16,
  сохранность пробелов и пустых строк, графемы в том числе на границах Markdown-узлов,
  восстановление тегов, переносы ссылок и кода.
- `DefaultLlmResponseFormatterLimitsTests.cs` — ограничения числа блоков и глубины,
  списки без лишних пустых пунктов, широкие таблицы, перенос строк таблицы целиком
  и продолжение длинной ячейки в той же колонке.
- `LlmResponsePartTests.cs` — оболочка `details`, экранирование заголовка и типизированные
  блоки для повторной отправки после ошибки HTML.
- `DefaultLlmChatHandlerTests.cs` — повторная отправка после ошибки разметки 400,
  отсутствие такого повтора для других ошибок и сообщений с похожими словами,
  уведомление о неполной отправке без записи в историю, сохранение чата, темы и реплая,
  отсутствие повтора при сбое хранилища после отправки и выбор непустого текста реплая,
  включая Rich Messages. В контексте реплая сохраняются адреса ссылок и заголовки `details`;
  исключается только служебный заголовок единственного внешнего блока нашего бота.

В коротких сценариях ожидаемые текст и HTML заданы явно. Для длинных ответов проверяются
сохранность текста, ограничения размера и структура каждой части; служебный корень в XML-проверках
позволяет проверять несколько соседних HTML-блоков. Эти проверки не заменяют проверку отображения
и принятия сообщения настоящим Telegram API.

Тест с `Currently` в названии явно фиксирует учёт скрытого URL в пороге сворачивания.
При намеренном изменении этого правила следует обновить ожидание и описание поведения.
Для чекбоксов проверяются состояния и текст пунктов, число пробелов после значка не фиксируется.
